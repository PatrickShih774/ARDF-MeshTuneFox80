# ADR-0005 中控 PC 软件技术栈待定

- 状态：**提议（待定）**
- 日期：2026-09
- 决策者：中控软件组 / 项目组

## 背景

中控 PC 软件（`software/master-console/`，规划中，待创建）需要完成三件事（见 [`software/README.md`](../../software/README.md) §3.1）：

1. 通过**串口 / USB-CDC / UDP** 与多台从机通信（可能同时连接多台，需处理多口并发）；
2. **实时遥测展示**：设备列表、状态刷新、曲线绘制、告警；
3. **赛事编排**：按六种模式生成发射窗口、台号分配、时间同步、冲突检查与赛报导出。

团队背景**偏嵌入式**（C / Python 为主，缺少桌面应用开发经验），
且项目当前处于**协议尚未定稿**的阶段：协议字段、时序、安全方案都可能调整。

此时若锁定技术栈，风险是：协议大改时被框架的结构绑住手脚；
团队若选了不熟悉的栈，会在学习成本上消耗本应用于协议验证的时间。

## 决策

**本轮不锁定中控技术栈**，采取"先原型、后定稿"的策略：

1. 先用 **Python（pyserial + FastAPI + 轻量 Web UI）** 做原型，
   目标是**验证协议与界面需求**：能否稳定解析帧、能否展示多机遥测、编排流程是否顺手。
2. 原型完成后，再决定是**继续沿用 Python** 做正式版，
   还是转向 **.NET / Avalonia（或 WPF）** 做发行版。
3. 决策时以三个问题为准：分发给赛场工作人员的体验是否可接受？
   长时间运行的稳定性是否足够？协议变动时的改造成本是否可控？

在此之前，`software/master-console/`（规划中，待创建，目录尚未存在）只保证**目录结构与职责边界**稳定，
不写任何与框架强耦合的实现代码。

## 后果

**正向**

- 迭代快：协议调试成本极低，改动一小时内可验证。
- 跨平台：Windows / Linux / macOS 开箱即用，赛场机器环境不受限。
- 生态丰富：pandas / matplotlib 做遥测曲线与赛报导出几乎是现成的。
- 推迟决策，避免在信息不足时做出难以回退的选择。

**负向**

- **打包分发体验不如原生**：PyInstaller 包体积大、启动慢，杀软误报概率高。
- **GUI 性能一般**：高刷新率曲线与大量设备卡片时可能力不从心。
- 串口高吞吐下需注意 GIL 与线程/异步模型的选择。
- 存在"原型转正式版"的返工风险：若最终转向 .NET，界面层基本重写。
- 技术栈未定 → 中控侧的 CI 与依赖锁定策略暂时无法最终确定。

## 备选方案

| 方案 | 现状 |
| --- | --- |
| **Python（pyserial + FastAPI + Web UI）** | **当前原型采用**，迭代最快 |
| **.NET + Avalonia / WPF** | 候选发行版方案：原生体验、单文件发布、强类型 |
| Electron + Node.js | 拒绝：体积大、内存占用高，串口生态需绕路 |
| Qt / C++ | 拒绝：开发效率低，团队无积累 |
