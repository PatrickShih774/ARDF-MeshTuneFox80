# 架构决策记录（ADR）

本目录存放本项目的 **ADR（Architecture Decision Record，架构决策记录）**。

## 1. ADR 的用途

ADR 记录**一次重要的技术决策**及其当时的背景、权衡与后果。它的价值在于：

- **避免重复争论**：为什么不用 Arduino、为什么是 6 只继电器，答案在这里，不必每次重开辩论。
- **保留上下文**：记录"当时知道什么、不知道什么"，避免用事后视角苛责旧决策。
- **明确边界**：把许可、分区、接口等约束固化为可引用的条目。
- **便于新人上手**：读完 ADR 就理解项目为何长成现在这样。

ADR 只记录**架构级**决策（影响多个模块、难以回退、涉及许可或成本）。
普通实现细节放进代码注释或 [`software/README.md`](../../software/README.md)，不写 ADR。

## 2. 编号规则

- 文件名：`ADR-XXXX-简短标题.md`，编号为 **4 位十进制、从 0001 递增**。
- 编号**永不复用**：即使某条 ADR 被废弃，其编号与其文件仍然保留。
- 标题用中文简述决策内容（"采用 X 而非 Y" / "X 方案"），避免过宽（如"架构设计"）。
- 新增 ADR 时**不得修改已接受 ADR 的正文结论**；如需变更，请新建 ADR 并在其中声明取代关系。

## 3. 状态取值

| 状态 | 含义 |
| --- | --- |
| **提议** | 已提出、尚在讨论，未生效，不应作为实现依据 |
| **已接受** | 已达成一致，所有后续实现必须遵守 |
| **已废弃** | 曾经接受，但当前不再执行（原因通常写在同一份 ADR 末尾） |
| **被取代** | 被编号更大的新 ADR 取代，须注明 `被 ADR-XXXX 取代` |

## 4. 模板

```markdown
# ADR-XXXX 标题

- 状态：提议 | 已接受 | 已废弃 | 被取代（被 ADR-XXXX 取代）
- 日期：YYYY-MM
- 决策者：<角色/团队>

## 背景

（现状、约束、问题、相关数据）

## 决策

（做了什么决定，边界在哪里）

## 后果

（正向 / 负向，尽量写可验证的影响）

## 备选方案

（考虑过什么、为何拒绝）

## 关联

（相关文档、目录、其他 ADR）
```

## 6. 写法约定

- 语言：中文；日期用 `YYYY-MM`（本批 ADR 统一为 `2026-09`）。
- 一份 ADR 应能在 **5 分钟内读完**，建议 40–70 行。
- 「后果」中的负向项必须写实，不允许只写好处。
- 涉及许可的 ADR 必须包含法律边界备注，不做法律担保。
